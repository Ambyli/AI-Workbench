# Claude Usage Observer

Windows system tray app that monitors Claude Code token usage. Reads local `~/.claude/projects/**/*.jsonl` logs and optionally scrapes account stats from claude.ai via Chrome DevTools Protocol (CDP).

## Commands

```bash
# Install deps
pip install -e .
# or
uv pip install -e .

# Run
python -m claude_observer
# or after install:
claude-usage-observer

# Debug CDP captures (requires Chrome on --remote-debugging-port=9222)
python -m claude_observer.browser.cdp_spy
```

## Threading Model — Read Before Touching Anything

This is the most likely place to introduce bugs. Three threads run concurrently:

1. **Main thread** — pystray event loop (`icon.run()`). Blocking this freezes the tray. All tray menu callbacks must spawn daemon threads immediately.
2. **Popup thread** — tkinter `mainloop()` in a daemon thread spawned on tray click. **All tkinter calls must happen on this thread.** Use `_win.after(0, fn)` to schedule from anywhere else — direct calls from other threads crash or hang.
3. **Fetcher thread** — `BrowserLinker._loop()` runs forever; when data arrives it calls `popup.update()`, which uses `after()` internally to stay safe.

## Browser / CDP — Non-Obvious Constraints

- CDP requires **an already-running Chrome instance** with `--remote-debugging-port=9222`. The app launches Chrome itself via `chrome_launcher.py`; it does not use Selenium.
- The 4-second sleep at the start of `_loop()` waits for Chrome to open the tab. Removing it causes reliable connection failures on startup.
- `interceptor.js` is read from disk **once at startup** and cached as a string. Editing the file while the app is running has no effect — restart required.
- **Do not reformat `interceptor.js`.** It is injected verbatim into the page as a CDP parameter. Reformatting can silently change behavior or break string injection.
- The interceptor uses `response.clone()` before reading the body. Removing this gives the page an empty body — the site breaks.
- The `_fetchInterceptorActive` guard prevents double-patching on re-injection. Do not remove it.
- If `requests` or `websocket-client` are uninstallable/missing, the entire account-stats feature silently disables — no error is raised.

## LLM Backend Toggle — Files Modified

`backend.py` modifies two files outside the repo:

- `~/.claude/settings.json` — adds/removes `env` overrides pointing at local llama-server
- `~/.claude.json` — swaps `primaryApiKey` to a dummy key

These are read-modify-write operations. If either file is open/locked by another process the operation may fail silently. After toggling, verify with `is_local_llm_active()`.

`stop_server()` calls `terminate()` but does not wait for exit — the process may briefly linger. There is no automatic cleanup on app quit; the llama-server process becomes orphaned if the user closes the tray without explicitly stopping it.

## Headless Session Logic

After a successful login, `fetcher.py` writes a sentinel file. On next launch, Chrome starts headless. If the headless session expires (login timeout), the code catches the error, deletes the sentinel, relaunches Chrome visibly, and sets status to `"waiting_login"`. Calling `go_headless()` before a successful login is a silent no-op.

`pyproject.toml` lists `selenium`, `trio`, and `trio-websocket` — none are used. The CDP approach replaced Selenium; `trio` is a legacy leftover. Safe to remove if cleaning up.

## LiteLLM with Phoenix MCP (Tool Calling)

The Phoenix MCP server exposes database tools via LiteLLM. The model receives tool definitions but LiteLLM does **not** execute the tool calls automatically — you must orchestrate the tool call loop.

### Step 1: Send the user message

```bash
curl http://localhost:4001/v1/chat/completions \
  -H "Authorization: Bearer sk-your-master-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.6",
    "messages": [{"role": "user", "content": "List all tables in the database"}]
  }'
```

The response will have `"finish_reason": "tool_calls"` with a tool call object.

### Step 2: Send the tool result back

Use the `tool_call_id` from the response and call the MCP tool directly, then send the result back:

```bash
curl http://localhost:4001/v1/chat/completions \
  -H "Authorization: Bearer sk-your-master-key" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.6",
    "messages": [
      {"role": "user", "content": "List all tables in the database"},
      {"role": "assistant", "tool_calls": [{"function": {"arguments": "{}", "name": "list_tables"}, "id": "CALL_ID_FROM_STEP_1", "type": "function"}]},
      {"role": "tool", "tool_call_id": "CALL_ID_FROM_STEP_1", "content": "[\"projects\", \"users\"]"}
    ]
  }'
```

Replace the `content` with the actual result from calling the tool on the Phoenix MCP server (`https://phoenix-mcp.com/mcp`).

### Phoenix MCP API Token

The Phoenix MCP server issues long-lived API tokens via a browser-based OAuth flow:

```bash
# Get a Google login URL
curl -s https://phoenix-mcp.com/api-token \
  -H "X-API-Key: your-shared-secret"
# Open the returned login_url in a browser, sign in, get your API token

# Or exchange a Google access token directly
curl -X POST https://phoenix-mcp.com/api-token \
  -H "X-API-Key: your-shared-secret" \
  -H "Content-Type: application/json" \
  -d '{"google_token": "<google-access-token>", "expires_in": 0}'
```

## Roofix ↔ Phoenix Bridge

`ai/roofix/` bundles the Roofix ↔ Phoenix subsystem: `bridge/` (event-sourced worker) and `scraper/` (Playwright proposal fetcher). One compose file (`docker-compose.roofix.yml`) brings up both. See [`ai/roofix/ROOFIX.md`](ai/roofix/ROOFIX.md) for the operator guide; a few things worth calling out here:

- **Default `DRY_RUN=true`**: on first deploy the bridge fetches Gmail, parses, decides, and logs — but does **not** write to Phoenix. Flip to `false` only after inspecting a full tick.
- **Bridge talks to Phoenix directly (psycopg2), not via MCP**: the earlier MCP variant was reverted because Phoenix MCP write tools weren't ready in time. Bridge needs `PHOENIX_DB_*` env vars set. `DRY_RUN=true` still short-circuits writes.
- **Bridge talks to Gmail directly (Google API + OAuth), not via MCP**: same reason. Requires `credentials.json` + `token.json` in `ROOFIX_BRIDGE_CONFIG_DIR`. First-time login is interactive — run `python components/gmail_client.py` locally once before shipping the token file into the container. See [ROOFIX.md § Gmail OAuth setup](ai/roofix/ROOFIX.md#gmail-oauth-setup).
- **AI fallback via LiteLLM**: `roofix/components/brain.py::generate_ai_decision` uses the OpenAI SDK against `http://litellm:4000`. Swapping Claude for a local vLLM model is a LiteLLM config change, not a bridge code change.
- **Session refresh is a manual operator flow**: the scraper cannot present a login UI. Run `save_roofix_session.py` locally on a laptop with a visible browser, then POST the resulting JSON to the scraper's `/session/refresh`.
- **Michael's mapping**: `ai/roofix/config/field_mapping.json` is a stub. Milestone writes will log "no milestone mapping" and skip until the file is filled in — this is intentional.

## Sandbox subsystem

`ai/sandbox/` runs untrusted, model-generated web apps (Streamlit, Gradio, Flask, FastAPI, Vite+React, Next, Express, static HTML) in short-lived isolated containers and exposes them to Open WebUI as iframe artifacts — the "artifacts panel" pattern, but for anything a real runtime can run. `sandbox-runner` is FastAPI + FastMCP; the model calls the `sandbox.run(runtime, files, entrypoint)` MCP tool (or the pipelined `create` → `write_files` (new files) → `read_file` / `edit_file` (changes) → `exec` → `preview` → `close` flow) via LiteLLM's MCP registration and gets back a URL to iframe. See [`ai/sandbox/SANDBOX.md`](ai/sandbox/SANDBOX.md) for the operator guide. A few things worth calling out here:

- **Network segmentation is the primary security control, not container hardening.** The subsystem uses FIVE Docker networks (the fifth, `sandbox_db_publish`, is a plain bridge with IP masquerade off that only `sandbox-db` joins, solely so Docker publishes `PORT_SANDBOX_DB`: it publishes nothing for a container on internal networks only, which silently broke Trino's `postgres_sandbox` catalog on Docker 29.4). The other four: `ai_shared` (external, so openwebui/litellm can reach the runner + proxy), `sandbox_net` (bridge, `internal: true` — sandboxed containers + the egress proxy), `sandbox_state` (bridge, `internal: true` — runner ↔ sandbox-db only), and `sandbox_egress_out` (bridge, NOT internal — the egress proxy's ONLY route to the public internet; nothing else attaches here). `internal: true` means Docker attaches no default gateway; a sandbox that tries to reach `litellm:4000` or `phoenix-mcp` gets no route, and the only escape hatch to the internet is `sandbox-egress`, which enforces the allowlist. If you add a service to `ai/sandbox/docker-compose.sandbox.yml`, keep the network memberships minimal and re-run the security-invariant checklist in SANDBOX.md.
- **`sandbox-runner` is the only container with `docker.sock` access.** It's the audit boundary. Any code that opens the socket must live in `ai/sandbox/runner/spawner.py` — that's the review focal point.
- **Egress is allowlisted, not blocked-by-default.** `sandbox-egress` (tinyproxy) reads [`ai/sandbox/proxies/tinyproxy.filter`](ai/sandbox/proxies/tinyproxy.filter) with `FilterDefaultDeny Yes`. Adding a new dep source is a filter-file edit + `docker compose restart sandbox-egress`. Never add `.*` — that defeats the model.
- **Base image port is always 80.** All runtime templates in `ai/sandbox/runner/runtimes.py` bind port 80 so `sandbox-proxy` (Caddy) can statically route `/{sandbox_id}/* → sandbox-{id}:80` with no dynamic config. Adding a new runtime that listens on something else means also adding dynamic Caddy admin-API management — don't unless you have to.
- **Job state is Postgres (`sandbox-db`), not SQLite.** Concurrent writers, JSONB metadata for operator queries via `psql`, and the DB lives on its own `sandbox_state` network so a container escape in a sandbox can't tamper with job records. `common.jobs.PostgresRegistry` is the reusable backend — any future service that wants Postgres-backed jobs can adopt it.
- **File tools follow Claude Code's contract — keep it that way.** `read_file` (numbered `offset` / `limit` window), `edit_file` (exact-string `old_string` → `new_string`, unique match or `replace_all`, closest region of the file on a miss), `write_files` only for new files (it refuses with `409 rewrite_of_existing_file` to re-send an existing 30+-line text file that keeps ≥ 50 % of its lines, unless `overwrite=true`), and short results (an edit returns a snippet, `exec` echoes one line of the command, content in the text is not repeated in `structured_content`). The edit / numbering / UTF-8 rules live in `common.textops` (pure, tested in `shared/common/tests/test_textops.py`); the rewrite-guard policy (thresholds, messages) and the tool wiring stay in the runner (tested in `unit-tests/sandbox/`). Any guidance string that tells a model which tool to use must teach this flow. A new runner module must also be added to the `COPY` list in `ai/sandbox/runner/Dockerfile`, or the image fails at boot. See [SANDBOX.md § Editing files](ai/sandbox/SANDBOX.md#editing-files).
- **Sessions + idle-TTL.** `create` / `run` return a `session_id` on first call; pass it back on `write_files` / `read_file` / `edit_file` / `exec` / `preview` to reuse the same running container. The reaper enforces both `SANDBOX_HARD_TTL_SECONDS` (absolute) and `SANDBOX_IDLE_TTL_SECONDS` (bumped on every session-reuse call via `metadata->>'last_used_at'`). Explicit teardown via `close(session_id)` MCP tool, `DELETE /session/{id}`, or the existing `DELETE /jobs/{id}`.

## n8n subsystem

`ai/n8n/` runs a self-hosted [n8n](https://n8n.io) workflow engine — used for stitching together LiteLLM, Roofix, MCP servers, and external HTTP surfaces without writing bespoke code for each automation. Compose file: [`ai/n8n/docker-compose.n8n.yml`](ai/n8n/docker-compose.n8n.yml). Operator guide: [`ai/n8n/N8N.md`](ai/n8n/N8N.md). A few things worth calling out here:

- **Reached at `/n8n/` under the shared oauth2-proxy, not a dedicated hostname.** `OAUTH2_PROXY_UPSTREAMS` in `.env` includes `http://n8n:5678/n8n/` — oauth2-proxy's longest-prefix routing sends `/n8n/*` to the n8n container, same pattern the sandbox subsystem uses for `/sandboxes/*`. The n8n container's `N8N_PATH`, `N8N_EDITOR_BASE_URL`, and `N8N_WEBHOOK_URL` env vars (all in `.env`) tell it it's mounted at that subpath and MUST stay in sync with `OAUTH2_PROXY_UPSTREAMS` — changing one without the other silently breaks routing. The shared oauth2-proxy cookie means one Google sign-in covers both Open WebUI and n8n. **No Cloudflare dashboard change is needed** — same hostname, new path prefix.
- **All container config lives in `.env`, not the compose file.** `ai/n8n/docker-compose.n8n.yml` is a pure `${…}` template — same discipline as `ai/openwebui/docker-compose.openwebui.yml`. Edit `.env` (the `## n8n subsystem` block), not the compose YAML.
- **`N8N_ENCRYPTION_KEY` is load-bearing and must persist across restarts.** It encrypts every stored credential blob in `n8n-db`. Rotating or losing it does NOT destroy workflow rows but permanently corrupts the encrypted credential fields — every saved OAuth token, API key, and password becomes unreadable. Generate with `openssl rand -hex 32`, paste into `.env` before the first start, back it up. The compose file uses `${N8N_ENCRYPTION_KEY:?...}` to fail fast if unset.
- **AI nodes are preconfigured against LiteLLM.** `N8N_AI_OPENAI_API_BASE` (in `.env`) points at `http://litellm:4000/v1` and the API key is sourced from `DEFAULT_LITELLM_MASTER_KEY`, so the OpenAI / LangChain credential picker defaults to the local model list — operators don't paste the base URL or key per workflow. Only override at the credential level when targeting an external provider (real OpenAI, Anthropic direct, etc.).
- **No queue mode / Redis broker.** Single-process runtime is enough for the current prototype workload; if execution backlog becomes real, flip `EXECUTIONS_MODE=queue` and add a Redis service — the Postgres backing DB already supports that migration.

## Open Terminal subsystem

`ai/open-terminal/` runs [Open Terminal](https://github.com/open-webui/open-terminal) (`ghcr.io/open-webui/open-terminal`) as the code-execution backend for Open WebUI, replacing the legacy in-browser Pyodide code interpreter: a real Linux container with Python, Node, gcc, ffmpeg and LibreOffice, a persistent per-user `/home`, wired into the chat as native function-calling tools plus a file-browser sidebar, upload target, and interactive terminal pane. Compose file: [`ai/open-terminal/docker-compose.open-terminal.yml`](ai/open-terminal/docker-compose.open-terminal.yml). Operator guide: [`ai/open-terminal/OPEN_TERMINAL.md`](ai/open-terminal/OPEN_TERMINAL.md). A few things worth calling out here:

- **Never on `ai_shared`, and never with `docker.sock`.** This is a root-capable shell a model drives. It joins a dedicated plain bridge, `terminal_net` (created by `make network`), whose only other member is `openwebui`. From `ai_shared` it could reach `roofix-db` / `sandbox-db` / `n8n-db` / `lake-s3` on their dev-default credentials, `litellm`, n8n's encrypted credential store, and `sandbox-runner` — which mounts `docker.sock`. The upstream image ships the Docker CLI and the README documents mounting the socket; doing that here would hand a model root on the host and make every other control decorative. `terminal_net` is NOT `internal: true` (unlike `sandbox_net`) because the fat image's whole point is runtime `pip` / `apt`; egress is narrowed inside the container by `OPEN_TERMINAL_ALLOWED_DOMAINS` instead, which needs `cap_add: [NET_ADMIN]`. Do **not** add `security_opt: [no-new-privileges:true]` — the image runs as an unprivileged user and needs passwordless sudo for the firewall, package installs, and account provisioning.
- **No host port, on purpose.** Every request is proxied by the Open WebUI *backend* (`backend/open_webui/routers/terminals.py`), which attaches `Authorization: Bearer` and `X-User-Id` server-side, so the API key never reaches a browser. Debug with `docker exec openwebui curl …`; the Postman collection documents the temporary-loopback and socat alternatives. Never bind `0.0.0.0` — the bearer token would be the only thing between the LAN and a shell.
- **Multi-user mode is a workspace separation, not a security boundary.** `OPEN_TERMINAL_MULTI_USER=true` maps each Open WebUI user id to a Linux account under `/home` (the `open_terminal_home` volume). Upstream says plainly that one kernel / one process list / one network stack means users are not protected from each other, and account provisioning needs privileges inside the container. Everyone with chat access must be trusted at the same level; real isolation is Open WebUI Enterprise "Terminals" (container-per-user, `server_type: "orchestrator"` + `policy_id` on the same connection shape).
- **Two first-boot-only PersistentConfig values.** `TERMINAL_SERVER_CONNECTIONS` (`terminal_server.connections`) and `ENABLE_CODE_INTERPRETER` (`code_interpreter.enable`) are read from env only on the first boot of a fresh `openwebui_data` volume — same trap as `ENABLE_WEB_SEARCH` and the `AUDIO_TTS_*` block. On this install set them at Admin Settings → Integrations → Open Terminal and Admin Settings → Code Execution. The connection JSON is built INLINE in `ai/openwebui/docker-compose.openwebui.yml` so `OPEN_TERMINAL_API_KEY` lives in exactly one place and the two containers can't drift.
- **Access control is `config.access_grants`, not `access_control`.** `utils/access_control.py::has_connection_access` treats a missing or empty list as *private, admin-only*, so a connection with no grants is invisible to regular users. Public read is `{"principal_type": "user", "principal_id": "*", "permission": "read"}`; group scoping swaps in `principal_type: "group"` with the group id.
- **Terminal tools are native function calling only.** A model configured with `function_calling: legacy` receives none of them — the terminal pill shows up and does nothing. Set those models to Native in Workspace → Models. Selecting a terminal also force-clears the Code Interpreter toggle in the composer, which is why `OPENWEBUI_ENABLE_CODE_INTERPRETER=false`; `ENABLE_CODE_EXECUTION` (the browser-side "Run" button on a code block) is deliberately left alone.
- **Adding `terminal_net` to `openwebui` changes its network list**, so applying it is `make up openwebui` (a recreate), not a restart.
- **The image is locally built (`open-terminal-zeo:<tag>`), same pattern as `openwebui-zeo`.** Upstream's entrypoint crashes at boot with `unable to raise CAP_SETPCAP for BSET changes` whenever the egress allowlist is set, because it calls `capsh` as the unprivileged user (open-terminal#119; fix PR #118 unmerged as of 0.13.0). `ai/open-terminal/Dockerfile.open-terminal` + `patch_entrypoint.py` apply that fix (`sudo -E capsh … --user=user`) and fail the build if the script has changed shape. When #118 ships, retire the Dockerfile and point the compose back at the upstream image — don't keep patching a fixed base.

## Trino data lake

`ai/trino/` bundles a Trino coordinator + Hive Metastore (+ its Postgres) + an S3 object store (`lake-s3`, RustFS) + Superset (+ its Postgres) + a FastMCP shim (`trino-mcp`) registered with LiteLLM. Federates SQL over the Postgres instances this repo runs (`litellm_db`, `roofix-db`, `sandbox-db`, `supabase-db`, the classifier's `classifier-db` as `postgres_classifier`, and the route-policy service's `route-policy-db` as `postgres_route_policy`) plus an Iceberg lakehouse on `lake-s3`. One compose file (`ai/trino/docker-compose.trino.yml`) brings up the whole stack. See [`ai/trino/TRINO.md`](ai/trino/TRINO.md) for the operator guide; a few things worth calling out here:

- **Two networks: `ai_shared` + `analytics_net`.** Data-plane traffic (Trino ↔ HMS ↔ HMS Postgres) stays on `analytics_net`. `ai_shared` carries only the surfaces external callers reach: `trino-coordinator` (JDBC / web UI), `lake-s3` (S3 API + console), `superset` (UI), and `trino-mcp` (LiteLLM MCP endpoint). `analytics_net` is a plain bridge — not `internal: true` — because `lake-s3` already publishes host ports on `ai_shared`, so hardening the data plane wouldn't gain anything and would complicate future ingestion jobs.
- **Catalogs are `.properties` files, not compose services.** Adding a new data source (real S3, GCS, BigQuery, or another Postgres) is: drop a file in `ai/trino/catalogs/`, reference its secrets as `${ENV:VAR}`, add those vars to `trino-coordinator`'s `environment:` block in the compose file AND to `.env` + `.env.example`, then `make up trino trino-coordinator` (recreate, not restart — the container env changed). Never add a compose *service* for a catalog. Hosted Postgres needs `?sslmode=require` on the URL; Supabase must use its session-pooler host (the direct host is IPv6-only); a `$` in any `.env` value must be written `$$`. Full recipe and templates in [ai/trino/TRINO.md § Adding a catalog](ai/trino/TRINO.md#adding-a-catalog).
- **Postgres federation reaches across subsystems via `host.docker.internal`, not Docker DNS.** `litellm_db` and `sandbox-db` don't live on `ai_shared`; the sandbox DB is deliberately isolated on `sandbox_state`. Trino reaches both through the host publish (`localhost:5432`, `localhost:5440`) to avoid breaching subsystem isolation. `roofix-db` is on `ai_shared` and uses service DNS, as do `supabase-db`, `classifier-db` and `route-policy-db` (each through its own read-only `trino_reader` role). If you ever want to unpublish `PORT_SANDBOX_DB`, the sandbox catalog stops working — that's intentional; the operator flips a `.env` port to sever the read path.
- **`trino-mcp` is SELECT-only by default.** `common.trino.TrinoClient` rejects everything except `SELECT`/`WITH`/`SHOW`/`DESCRIBE`/`EXPLAIN` unless `allow_writes=True` is set — only `ai/trino/bin/init_warehouse.py` does that. Rows are clamped to `TRINO_MCP_MAX_ROWS` (spliced `LIMIT` if the SELECT doesn't include one); runtime is clamped to `TRINO_MCP_MAX_RUNTIME_S` via `session_properties.query_max_execution_time`. The coordinator's own `query.max-execution-time` in `ai/trino/config/config.properties` is the belt-and-suspenders backup.
- **The coordinator has two listeners with different trust models — never publish the HTTP one.** `:8443` (HTTPS, password-file auth, self-signed cert) is what `PORT_TRINO` maps to; `:8080` (plain HTTP) is re-enabled via `http-server.authentication.allow-insecure-over-http=true` and authenticates by username only, exactly like every other service on `ai_shared`. `trino-mcp`, Superset, `init_warehouse.py`, and the healthcheck all use 8080 by Docker DNS. Adding an 8080 `ports:` mapping would hand LAN users a password-free bypass. Cert + `password.db` come from the one-shot `trino-auth-init` service (`ai/trino/auth-init/`) into the `trino_auth` volume; users are `TRINO_JDBC_USERS` in `.env`.
- **Superset uses `AUTH_TYPE=AUTH_REMOTE_USER` — the header-auth trust boundary is load-bearing.** oauth2-proxy sets `X-Auth-Request-Email` on every authenticated request; Superset trusts it as the session user with NO password check. `PORT_SUPERSET` (default 8016) is published by `ai/edge`, which deletes `X-Auth-Request-Email` / `-User` / `-Preferred-Username` and `X-Forwarded-Email` / `-User` on that listener — oauth2-proxy reaches `superset:8088` directly, so a header arriving there is always a spoof. Never route oauth2-proxy through the edge, and never remove those `del-header` lines; if `SUPERSET_REMOTE_USER_HEADER` changes, add a `del-header` for the new name. Before exposing the host on an untrusted network, still bind that edge port to loopback, or drop it and reach Superset only via `chat.zeoenergy.com/superset/`. Same trust posture as Open WebUI's `WEBUI_AUTH_TRUSTED_EMAIL_HEADER`.
- **Iceberg on RustFS uses `s3a://warehouse/`, not `s3://`.** The Hive Metastore's `hive.metastore.warehouse.dir` points at `s3a://warehouse/`, and every `CREATE SCHEMA` should include an explicit `WITH (location = 's3a://warehouse/<schema>')` — matches HMS's default filesystem, avoids the scheme-mismatch that would happen if Trino tried to write via the native S3 connector while HMS validated with s3a. `ai/trino/bin/init_warehouse.py` follows this convention.

## Supabase subsystem

`ai/supabase/` runs a full self-hosted Supabase on the box as a first-class compose subsystem: Postgres 17, an Envoy API gateway, GoTrue auth, PostgREST, Realtime, Storage + imgproxy, postgres-meta, Studio, Edge Functions, and the Supavisor pooler. It is the **service**, not an application — this repo creates no application tables in it. One compose file (`ai/supabase/docker-compose.supabase.yml`) brings up all eleven services. See [`ai/supabase/SUPABASE.md`](ai/supabase/SUPABASE.md) for the operator guide; a few things worth calling out here:

- **All root `.env` vars are `SUPABASE_`-prefixed and mapped onto upstream's unprefixed container env names inside the compose file.** Upstream's raw names are generic (`POSTGRES_*`, `JWT_SECRET`, `ANON_KEY`, …) and would collide with other subsystems in this repo's shared `.env`. Same consequence for secret generation: upstream's `utils/generate-keys.sh` `sed`s those unprefixed names into `./.env`, silently rewriting whatever else uses them. Use `ai/supabase/bin/generate_keys.py` instead (stdlib only, only ever touches `SUPABASE_*` lines). Edit `.env`, never the compose YAML — it is a pure `${…}` template, same discipline as `ai/n8n` and `ai/openwebui`.
- **Upstream service KEYS are kept verbatim; container names carry upstream's `supabase-<svc>` prefix.** The vendored Envoy cluster config (`ai/supabase/volumes/api/envoy/cds.yaml`) addresses the data plane by upstream's short hostnames — `auth`, `rest`, `realtime-dev.supabase-realtime`, `storage`, `functions`, `meta`, `studio` — so renaming a key 503s that gateway route. Realtime needs `realtime-dev.supabase-realtime` added as an explicit **network alias** on `supabase_net`, because upstream gets that DNS name from a dotted `container_name` we don't reproduce. Seven data-plane services (`auth`, `rest`, `storage`, `imgproxy`, `meta`, `studio`, `functions`) are swapped side by side on `make up`, so they have no `container_name` — the `com.zeo.deploy.name: supabase-<svc>` label names them `supabase-<svc>-<hash>`; `realtime` (replication slot) keeps `container_name: supabase-realtime`. Only the three services that also join `ai_shared` get a distinctive name for both: `supabase-db`, `supabase-api`, `supavisor`.
- **`supabase-db` is dual-homed onto `ai_shared` on purpose.** That is how `trino-coordinator` reaches it by service DNS (`supabase-db:5432`) for the `postgres_supabase` catalog, exactly like `roofix-db` — without the coordinator joining `supabase_net`. The trade-off is that anything on `ai_shared` can open a TCP connection to Postgres, so authentication is the only gate. Catalog naming follows `ai/trino/TRINO.md § Naming`: `postgres_<subsystem>` because this is a Postgres we run, while `supabase_ai_agents` / `supabase_enerflo_leads` stay `supabase_<project>` for supabase.com-hosted projects. Only the `postgres` database is federated — `_supabase` (Supavisor's metadata DB) is not.
- **The `trino_reader` role is the only DB object this repo creates**, via `ai/supabase/volumes/db/trino-reader.sql` at first init. `BYPASSRLS` is not optional: without it every RLS-enabled table reads as **zero rows** in Trino with no error. The script is idempotent and can be re-run with `psql` to retrofit an existing volume or rotate the password.
- **Four secrets are effectively one-shot.** Supavisor stores the database password in its tenant row encrypted under `VAULT_ENC_KEY`; Realtime stores its tenant's `jwt_secret` encrypted under `DB_ENC_KEY`. Rotating `SUPABASE_POSTGRES_PASSWORD`, `SUPABASE_JWT_SECRET`, `SUPABASE_VAULT_ENC_KEY` or `SUPABASE_REALTIME_DB_ENC_KEY` after first boot needs those tenant rows re-seeded by hand — documented, deliberately not automated. Everything else rotates with a recreate.
- **Legacy HS256 API keys; the ES256 / `sb_publishable_…` pair is a follow-up.** `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_ANON_KEY_ASYMMETRIC`, `SUPABASE_SERVICE_ROLE_KEY_ASYMMETRIC`, `SUPABASE_JWT_KEYS` and `SUPABASE_JWT_JWKS` ship **empty on purpose** — Envoy's entrypoint then logs `legacy API key mode` and carries on. `SUPABASE_JWT_JWKS` is the sharp one: PostgREST reads `${SUPABASE_JWT_JWKS:-${SUPABASE_JWT_SECRET}}`, so a non-empty value flips it to asymmetric verification and every legacy key stops working.
- **The upstream `logs` override (Logflare + Vector) is not added** — Vector needs `/var/run/docker.sock`, and `sandbox-runner` is the only container permitted to mount it here (it is the audit boundary; see `ai/sandbox/SANDBOX.md`). Upstream no longer ships analytics in its *base* compose either, so this is a matter of not layering the override rather than deleting services. `volumes/db/logs.sql` **is** still mounted for parity — it only creates the `_analytics` schema inside `_supabase`, so enabling the override later needs no manual schema step. Studio's Logs pages have no backend as a result (`ENABLED_FEATURES_LOGS_ALL=false`).
- **LAN-facing only.** No oauth2-proxy, Cloudflare tunnel, or Google OAuth in front of it; the gates are Envoy basic auth on Studio and the API keys on everything else. Public exposure via `supabase.zeoenergy.com` is a flagged follow-up, not an oversight.
- **`ai/supabase/volumes/` is vendored upstream config and must stay LF.** The Postgres init scripts use psql's `` \set x `echo "$VAR"` `` trick, where a trailing `\r` bakes a carriage return into the value — producing, for example, a role password that silently does not match. `.gitattributes` forces `eol=lf` on `*.sql`, `*.exs`, `*.ts` and `*.jsonc` for exactly this reason. Named volumes replace upstream's `./volumes/db/data` and `./volumes/storage` bind mounts, and the `:z` / `:Z` SELinux flags are dropped.

## LiteLLM chains and hooks

`ai/litellm/` is the single OpenAI-compatible surface. Chat traffic is routed through four **chain aliases** — `local-private` (PII), `local-code`, `local-reasoning`, `local-general` (catch-all) — each a model group whose deployments LiteLLM tries by `order`: local first, Claude only as overflow, never for `local-private`. The alias `auto` is decided per request by the route-policy engine (see the next section) and served in ONE pass. The behaviour lives in LiteLLM's custom hooks (`ai/litellm/hooks/`) and `litellm_config.yaml`. Compose file: [`ai/litellm/docker-compose.litellm.yml`](ai/litellm/docker-compose.litellm.yml). Operator guide: [`ai/litellm/LITELLM.md`](ai/litellm/LITELLM.md). A few things worth calling out here:

- **`auto` is single-pass.** `auto` is `router_settings.model_group_alias: {auto: local-private}` — no `model_list` entry, no `fallbacks` / `context_window_fallbacks` / retry-policy entry (those are looked up by model group, so they would never apply after the rewrite). The alias is resolved only at deployment selection (`router.py:10465` at v1.95.0), **after** the pre-call hook (`common_request_processing.py:1274`), so the hook still sees `"auto"`; it is listed in `/v1/models` (leave `hidden` unset — Open WebUI lists it) and passes key checks. The hook awaits route-policy `POST /decide` (`ROUTE_POLICY_DECIDE_TIMEOUT_S`, 0.25 s, `asyncio.wait_for` — LiteLLM puts no timeout around pre-call hooks, `proxy/utils.py:1444`), rewrites `data["model"]` to the returned chain when `apply` is true and its own invariants agree (`hooks/routing/invariants.py`, a copy of the service's `engine/invariants.py`; `unit-tests/litellm` loads both files by path and runs them over the same cases), and LiteLLM serves that chain in the same pass, **streamed**. Anything else — timeout, non-200, bad JSON, `apply: false`, the client off — goes to `local-private`, counted and logged as `[route-policy] auto -> local-private (<why>)`; and a request the hook never rewrote is served by `local-private` through the alias anyway. The stash (`zeo_route_policy` in the proxy's metadata dict — `data["metadata"]`, or `data["litellm_metadata"]` on `/v1/messages`: `requested_model`, `route`, `source: engine | fallback:<why>`, `decision_id`) is what the footer and `/observe` read, never `data["model"]`; neither dict reaches the upstream. `/decide` gets the conversation with every inline base64 / `data:` payload in a content part replaced by a short placeholder (the part keeps its type; text and tool calls are verbatim), plus `background_task` (`hooks/footer/render.py::is_openwebui_task(data)`, the footer's own detection of a non-streamed Open WebUI title / tags / follow-up request — computed in the hook because it needs `data["stream"]`). Each tool round of an Open WebUI answer, and the hidden auto-continue nudge, is its own `auto` request; the service keeps one chain per answer (`pin: turn`, below) — the hook keeps no state for it. The client still sees `"model": "auto"` (`requested_model_from_client`), and each request is ONE spend-log row under the caller's own key. Only `auto` is decided: a request naming a chain alias is served as asked. `/v1/messages` (Claude Code) to `auto` runs the same pre-call pipeline (`anthropic_endpoints/endpoints.py:95`), so it is routed too. One `auto` turn is one chain request — no fan-out, no quality escalation to Claude.
- **Chains, order, and the binding constraint: local vLLM slots.** `local-general` / `local-code` = `qwen3.8-solo` → `muse-glimmer` → `claude-sonnet-5`; `local-reasoning` = `muse-glimmer` → `qwen3.8-solo` → `claude-opus-5-5`; `local-private` = `qwen3.8-solo` → `muse-glimmer`, **no Claude**. Each deployment calls its vLLM / Anthropic backend directly, so a chain can never recurse. `qwen3.8-solo` has `--max-num-seqs 3`, `muse-glimmer` has 8 (`--max-num-seqs 8`), of which the classifier takes at most 6 (`max_concurrent: 6` on its entry in `ai/classifier/models.yaml`, called directly, not via LiteLLM) so that 2 stay free for chat — a classifier that filled every sequence would keep `vllm:num_requests_waiting` above 0 and make the overflow hook spill every chat turn off `muse-glimmer`. `muse-glimmer` shares its GPU pair with `qwen3.8`; when an operator runs `qwen3.8` instead, the overflow hook sees `muse-glimmer`'s `/metrics` fail and marks it down, so chains degrade to `qwen3.8-solo` alone. `qwen3.6`, `qwen3.8`, `qwen3.8-flash`, `glm5.2` are in no chain; `glm5.3-flash` stays out on purpose (CPU-only, one slot, minutes to first token). Chains need no `fallbacks` entries: a failed order is retried at the next order in-group (`router.py:6132-6182`), and `router_settings.model_group_retry_policy: {TimeoutErrorRetries: 0}` on the four chains sends a pre-header timeout straight to the next order instead of retrying order 1.
- **Privacy: `local-private` is the safe place, and every failure path ends there.** It has **no Claude deployment and no entry in `fallbacks` or `context_window_fallbacks`** (a loud comment in `litellm_config.yaml` says never add one): both locals busy → it queues locally; both down → it fails. The concrete aliases (`qwen3.8-solo`, `muse-glimmer`) keep their own `fallbacks: → claude-sonnet-5`, which is why nothing routes PII to them directly — LiteLLM re-reads the fallback map per hop (`router_utils/fallback_event_handlers.py:120-137` at v1.95.0, up to `ROUTER_MAX_FALLBACKS=5`). Every `auto` turn the engine did not route (route-policy slow, failing or down, `apply: false`, the alias itself) goes to `local-private`, because nobody has checked that prompt for PII. Remaining soft spot: the privacy rule is lexical — a PII prompt that names no `privacy_kw` word lands on another chain and can overflow to Claude.
- **`local-code` differs from `local-general` only per deployment** in `litellm_config.yaml`: one coding `litellm_system_prompt` (a YAML anchor `&code_system_prompt` reused on all three orders — never put a "Reasoning strength" line in it, Muse Glimmer's template would let it override the kwarg), `chat_template_kwargs` `reasoning_effort: high` on qwen (→ `xhigh` in the fixed template) and `reasoning_strength: xhigh` on muse, `max_tokens: 32768` (so qwen's `max_input_tokens` is 98304 and muse's 229376 there). A client `max_tokens`, `extra_body` or `chat_template_kwargs` still replaces the deployment's — see `ai/litellm/LITELLM.md § local-code: what it adds`.
- **The overflow hook is what makes "busy" spill, not just "down".** `ai/litellm/hooks/overflow/` (run from `Handler.async_filter_deployments` in `ai/litellm/hooks/handler.py`) is a `CustomLogger.async_filter_deployments`, which LiteLLM v1.95.0 calls in `async_get_healthy_deployments` **before** the pre-call context check and the order filter (`router.py:10686` → `10694` → `10716-10720`). Its first step is **context fit**: for a long prompt it asks each local vLLM's `/tokenize` for the exact count (`messages` + `tools`) and hard-drops a deployment the prompt does not fit against its `model_info.max_input_tokens` and `max_model_len` (`OVERFLOW_TOKENIZE_*`); LiteLLM's own `enable_pre_call_checks` is only the backstop — it counts with tiktoken over `messages` alone, so it undercounts Qwen prompts and ignores tool definitions. Context fit counts what LiteLLM will actually send: a deployment's `litellm_system_prompt` merged into the first system message, and the ONE `chat_template_kwargs` LiteLLM sends (request top-level, else request `extra_body`, else the deployment's — LiteLLM replaces, it does not merge). When no local deployment fits, a chain with Claude keeps only Claude — except for a request the client sent as `auto` (the route-policy stash in `request_kwargs`' metadata), which keeps its local deployments so vLLM refuses it: busy / down still overflow to Claude, length never does (what the old `auto` deployment's `max_input_tokens` used to enforce). A background task probes every local backend's `/metrics` concurrently about once a second; a backend whose `vllm:num_requests_waiting` has been > 0 for `OVERFLOW_BUSY_AFTER_S`, or whose probe fails, is dropped from chain groups so the next `order` answers. It never drops a deployment without an `api_base` (Claude), never empties a group (`local-private` queues instead), ignores data older than 5 polls, and never throws — LiteLLM re-raises a filter exception (`router.py:7366-7384`), which would fail the request. Spills log as `[overflow]` in `make logs litellm`; the spend log (model group = chain, model = deployment) is the cost record.
- **The hooks package loads through a shim, and the leaf-class rule is load-bearing.** `litellm_settings.callbacks: ["overflow.handler"]` makes LiteLLM exec `ai/litellm/overflow.py` (mounted at `/app/overflow.py` beside `/app/config.yaml`) via `spec_from_file_location` without registering it in `sys.modules` — relative imports fail there and a `@dataclass` crashes the proxy at import. So `overflow.py` is only a **shim**: it puts its own directory first on `sys.path`, imports the `hooks` package normally (mounted read-only at `/app/hooks`), removes that entry again (the proxy already *appends* `/app`; leaving it first would let `/app/*` shadow installed packages) and builds `handler`. Keep logic and `@dataclass` out of the shim; inside `hooks/` both are safe (`BackendState` is a dataclass). The package's layout is in `ai/litellm/hooks/__init__.py`, every env read is in `hooks/settings.py`. `hooks` imports one stdlib-only part of `shared/common`, `common.conversation`, bind-mounted at `/app/common/conversation` with `common/__init__.py`: the container is upstream plus mounts, so `common` is not installed there, and a new `common.<x>` import needs its own mount line. `unit-tests/litellm/test_hook_package.py` enforces that, stdlib-only `common` parts, and image-only third-party imports, and loads the shim in a fresh `/app` built from the compose mounts; `test_overflow.py` loads it through LiteLLM's own `get_instance_fn`. All five LiteLLM hooks must stay in `Handler`'s own class body (`hooks/handler.py`) and delegate from there to the components (`OverflowFilter`, `AutoFooter` / `FooterStream`, `PolicyClient`), because the proxy activates the streaming-iterator and pre-call hooks only when they are in the leaf class's `__dict__` (`proxy/utils.py:1718-1745`). The pre-call hook runs `AutoFooter.strip_incoming` (old footers out of the history, so the engine never reads them) and then `PolicyClient.route`. The same handler stamps every `auto` answer with a footer naming the chain and deployment that served it (`*qwen3.8-solo · local-general*`, from `data["deployment"]`; toggled by `AUTO_FOOTER_ENABLED`, `ai/litellm/hooks/footer/`).
- **Timeout budget: Open WebUI 900 > chains 240 / 300 per read.** `auto` streams now, so per-read timeouts are real and the old nested layers (`auto` 870, Envoy 840) are gone: Open WebUI `OPENWEBUI_AIOHTTP_CLIENT_TIMEOUT` / `_STREAM_IDLE_TIMEOUT` **900** (a hard total including streaming — and it bounds *every* chat completion, not just web search) > the chain deployments' per-read **240** (local orders 1–2) / **300** (Claude order 3). The edge's `listen litellm` (900 s client/server, `ai/edge/haproxy.cfg`) sits outside, crossed only by LAN clients. A turn can still be silent for minutes before its first chunk (queued behind a busy vLLM, prefilling a long prompt), which is why the Open WebUI idle timer stays at 900. `unit-tests/litellm/test_timeouts.py` enforces the order; see `ai/litellm/LITELLM.md § Chain timeouts`. The awaited `/decide` (0.25 s) adds to every `auto` turn's latency.

## Signals subsystem

`ai/signals/` is route-policy's CPU sidecar (phase 5 of ZT-471): small ONNX / fastText models that turn a conversation's texts into the features route-policy's signal evaluators vote on, fast enough for the turn being decided. One service, `signals` (FastAPI, `signals:8000` on `ai_shared`, no auth, like the classifier). Compose file: [`ai/signals/docker-compose.signals.yml`](ai/signals/docker-compose.signals.yml). Operator guide: [`ai/signals/SIGNALS.md`](ai/signals/SIGNALS.md). A few things worth calling out here:

- **Four tasks, pinned models, baked in, CPU only.** `pii` — `gravitee-io/bert-small-pii-detection` (BERT-small NER, Apache-2.0), its labels mapped onto `common.pii`'s vocabulary (a `LOCATION` span with a digit is `street_address`, without one `location`, which never forces); `nearest` — `intfloat/multilingual-e5-small` embeddings (MIT) + kNN over a ruleset's labelled examples; `injection` — `NeuralTrust/prompt-guard-oss-small` (MIT; fp32 — int8 broke the guards in the measurement); `language` — fastText `lid.176.ftz` (**CC-BY-SA-3.0**, used unmodified and internally; its attribution is in `SIGNALS.md § Models` and the image's `/models/language/NOTICE.txt` — keep both). `ai/signals/models.yaml` pins each by repo, revision (commit sha) and sha256 per file; the Dockerfile downloads at **build** time, verifies every hash and runs `python -m signals.runtime --check` (load, a warm-up inference, fabricated smoke answers), so a broken pin fails the build, never a request; at run time nothing downloads (`HF_HUB_OFFLINE=1`). No torch, no transformers. A model change is a `models.yaml` edit + `make build signals` + a new route-policy ruleset version for every evaluator that pins that model id (until it is bound they abstain with `model mismatch`, never route).
- **One batched call per decision, inside a 0.1 s budget.** Route-policy merges its evaluators' requests into ONE `POST /signals` (texts by id, newest first, each task once), sent concurrently with its database reads within `ROUTE_POLICY_SIGNALS_BUDGET_S`, with `deadline_ms` = the budget − 20 ms (80 ms). Each model has its own single-flight lane (one onnxruntime session, `SIGNALS_THREADS_*` threads); a job not started by its deadline is `skipped`, never run late (a back-to-back burst built an unbounded backlog in the prototype — `test_a_burst_never_builds_a_backlog`), and only a running PII job finishes after the answer, to fill the cache for the next call (at 2,000 characters PII answers `partial` and the next turn reads the rest from the cache). The process runs `sys.setswitchinterval(0.001)` (`config.GIL_SWITCH_INTERVAL_S`): at CPython's 5 ms default the event loop waited for the GIL behind three busy lanes and answered past route-policy's cut, which then dropped every partial result — keep it. A request with no deadline (`deadline_ms: null`: route-policy's `/evaluate`) is *patient*: its jobs queue in the background and hand the model to any request with a deadline between two steps (parked, then resumed; a parked patient job is never replaced), so a 20-text `/evaluate` can never make a `/decide` answer `skipped`. Task statuses `ok | partial | deadline | skipped | warming | error | unavailable`; a text that fails costs only that text (`partial`, `error` = the first failure's type; `error` only when no text has features); any but `ok` / `partial` is an abstain, so a slow, down or wrong sidecar never moves a turn. Caps (413): 20,000 characters per text, 200,000 per request, 64 texts. `/health` is 503 until every model is loaded and warmed (~10 s) — the compose healthcheck, the swap gate and the edge's check. The wire format and the client are `common.signals`, shared with route-policy.
- **It never logs or stores text.** Responses, logs, metric labels and error strings carry types, counts, scores, example ids and statuses — never text, spans or offsets (an exception becomes its type name); `read_only: true` + a tmpfs `/tmp`, no volume, no database, no outbound call, `cap_drop: [ALL]`. The only state is an in-memory LRU of `sha256` → features (`SIGNALS_CACHE_ENTRIES`) and the embedded example sets (keyed by fingerprint). `unit-tests/signals/test_signals_privacy.py` checks every response, log record and metric with a sentinel string; route-policy's client sends nothing to a host that resolves off the box's networks.
- **Swap-class, pinned to its own cores.** `com.zeo.deploy: swap`, no `container_name` / `ports:`, `stop_grace_period: 15s`; `PORT_SIGNALS` 8025 is published by `ai/edge` (`listen signals`). During a swap Docker DNS gives both copies traffic — equal model ids make that harmless. `cpuset: "${SIGNALS_CPUSET-24-31}"` (the box's 32 vCPUs: 24–31 here, 0–15 for `qwen3.5-4b`, 16–23 for the rest; empty = unpinned), `cpu_shares: 2048`, `mem_limit` `SIGNALS_MEM_LIMIT` 4g (~1.8 GB per copy, two during a swap). Measure on the box with `make exec signals signals CMD='python -m signals.bench'` (`--threads 1,2,4 --n 30`; it loads a second copy of the models on the same cores, so run it when the box is quiet).
- **Deploy order:** `make up edge` (it gains 8025) → `make build signals && make up signals` → `make build route-policy && make up route-policy` (seeds `default-signals@1`, adds the shadow slot, warms its example set — the Makefile registers `signals` before `route-policy` for this) → `docker restart prometheus` (job `signals`). Rollback: `git revert`, `make up route-policy`, then `docker compose -p ai-signals down` and `make up edge`. Tests: `unit-tests/signals` (fake models through the real scheduler, cache, API and privacy code; `test_signals_real_models.py` skips unless the pinned files are present).

## Route policy subsystem

`ai/route-policy/` is the route-policy engine (ROUTE_POLICY_PLAN, ZT-471): a **ruleset** of **evaluators** votes on which LiteLLM **chain alias** an `auto` turn should use, a **combiner** (`priority` / `weighted`) picks one route, and every decision — each evaluator's vote, and later what really answered — is logged to its own Postgres, which Trino reads as `postgres_route_policy`. Two containers: `route-policy` (FastAPI, swap-class, `route-policy:8000` on `ai_shared`) and `route-policy-db` (`postgres:17-alpine`, recreate-class). Compose file: [`ai/route-policy/docker-compose.route-policy.yml`](ai/route-policy/docker-compose.route-policy.yml). Operator guide: [`ai/route-policy/ROUTE_POLICY.md`](ai/route-policy/ROUTE_POLICY.md). A few things worth calling out here:

- **Phase 3: the engine routes `auto`.** The `default` ruleset (version 3) is `mode: enforce`: LiteLLM's pre-call hook (`ai/litellm/hooks/routing/policy_client.py`) **awaits** `POST /decide` (`ROUTE_POLICY_DECIDE_TIMEOUT_S`, 0.25 s), serves the returned chain in the same pass when `apply` is true and its own invariants agree, and sends everything else to `local-private`; `POST /observe` is still fired after the call, never awaited. Phase 2 ran the same rules in `shadow` beside the vLLM Semantic Router and LiteLLM's code-tool remap and agreed with them on real traffic; phase 3 deleted both (rollback: `git revert` + `ai/route-policy/ROUTE_POLICY.md § Upgrading from phase 2`). A `shadow` ruleset still works — decided and logged, never applied; bind one to a test `key_alias` to try a change, or beside a primary as a shadow slot (below).
- **Phase 4: the `llm_classifier`, in shadow.** It votes from a verdict a LOCAL model gave the conversation, classified in the BACKGROUND through the document classifier's existing `POST /assess` (no new classifier endpoint): the transcript (`common.conversation.render_transcript(..., upto_user=k)`) is one `text` document, each route one `llm` presence criterion (≤ 200 chars), `model` a registry id (`qwen3.5-4b`, the CPU llama.cpp service). Route-policy polls the job, reads the scores and usage, then **always `DELETE /jobs/{id}`** (the classifier would keep the text as a payload / text-layer artifact until `JOB_TTL_HOURS`; the delete takes the job's `llm_calls` too, so the usage is copied into route-policy's `analyses` row first). **Locality guard:** nothing is submitted unless the model's `GET /models` entry is `authenticated: false` and `available: true` AND every address its `endpoint.host` resolves to (from inside route-policy, on `ai_shared`) is in `common.net.DEFAULT_BLOCKED_NETWORKS` — a public address or an unresolvable host is `not_local` (a stopped model container is too: Docker DNS only answers for running ones). The verdict (`analysis.verdict.choose`: best score ≥ `min_score`, ties by the ruleset's `routes` order, else `otherwise`) is stored in `analyses` under `input_key = sha256(fingerprint, transcript)` — keyed by the conversation prefix, so tool rounds of one message share one classification, an edited earlier message can never reuse an old verdict, and no chat id is needed; at `/decide` for user message n the evaluator reads the keys for n … n − `max_age_exchanges` in ONE query (`DB_READ_BUDGET_S`) and votes the newest usable one, so it applies **from the next turn on**. The analysis queue (`route_policy/analysis/queue.py`) is **in memory** on purpose — bounded (`ROUTE_POLICY_ANALYSIS_QUEUE_MAX`), deduplicated by key, `ROUTE_POLICY_ANALYSIS_CONCURRENCY` workers; a lost analysis costs one turn's verdict. **No conversation text is ever stored or logged**: `analyses` keeps the hash, scores, route, usage and the winning criterion's reason (≤ 200 chars, CHECKed) — the only model-written text. Known limits: route jobs share the classifier's FIFO with document jobs (a backlog shows as lower coverage / higher `queue_ms`), and on `/v1/messages` a tool-result-only user message counts as a user message, so Claude Code verdicts age per tool round. The benchmark (`ai/route-policy/bench/`, `BENCH.md`) runs the same `/assess` cycle offline; promotion is a NEW `default` version adding `topic-llm`, only after its report passes.
- **Shadow bindings and the `default-llm` draft.** `bindings.yaml` entries take `shadow: [<id> | {ruleset, version}]` (table `binding_shadows`); seeding refuses a primary that is not `mode: enforce` and a shadow slot that is not `mode: shadow`. `store.resolve` returns `Resolved(primary, shadow refs)`; `/decide` answers with the primary EXACTLY as before, then ONE background task (counted in `WRITES_MAX_IN_FLIGHT`) enqueues the primary's analysis requests and runs each shadow on the same request: its own lookup, pipeline, a `decisions` row with `decision_id = uuid5(primary_id, "<ruleset>@<version>")` and `shadow_of = primary_id` (no FK), its own `evaluations`, its analysis requests — a repeated `/decide` re-derives the same ids. A shadow that fails to load or raises is skipped and counted (`shadow_load` / `shadow_error`), each shadow on its own (one that raises never skips the next); every exception route-policy logs or stores — an evaluator's `evaluations.error` / vote reason included — is its TYPE name only, since a message can quote the conversation. `decision_outcomes` now covers primaries only (0002 recreated it with the same columns); the `shadow_comparisons` view puts each shadow beside its primary and the served chain (`agree_with_primary`, `agree_with_served`); `GET /chats/{id}/decisions` nests `shadows`. `default-llm` (version 3; `mode: shadow`, `pin: turn`, bound as `auto`'s shadow) is `default`'s privacy / code / reasoning / tool rules in the same order plus `topic-llm` instead of `sticky-code`; the primary never sees it, so **a shadow never changes routing**. Version 2 reworded `topic-llm`'s code criterion ("asks to write, fix, change or explain source code, a script or a software project. Using a tool such as web search does not count.") after version 1's "writing, running, debugging or changing code or software" scored a web search for the weather 10/10 as running software. Version 3 shows `topic-llm` **only the latest user message** (`history.exchanges: 1`, was 4 — with 4 exchanges in the window, weather follow-ups scored 10/10 for code because earlier calculator work was still in it), counts a verdict for the next message only (`max_age_exchanges: 1`), and lets the code criterion cover building an app again ("asks to build, write, fix, change or explain software: an app, a website, a script or source code. Using a tool such as web search does not count." — version 2 scored "make me a calculator app" 1/10). Migration `0002_llm_classifier.sql` adds `binding_shadows`, `decisions.shadow_of`, `analyses` and the views — only additions, so rolling back is a revert + `make up route-policy`.
- **One route per turn (`pin: turn`), and background tasks** (`default@3`, `default-llm@2`, migration `0003_turn_pins.sql`). A ruleset with `pin: turn` holds every `/decide` of one answer — the same Open WebUI `chat_id` + `message_id`: its tool rounds, and Open WebUI's hidden auto-continue nudge (patch 0004 sends it as an extra USER message under the same message id, which `sticky-code` would otherwise count as a new exchange) — to the route of the turn's FIRST stored decision of that ruleset id (any version; `decisions_repo.first_of_turn`, ONE query on `decisions_turn_idx` within `DB_READ_BUDGET_S`, concurrently with the verdict lookup; a timeout / failure / no database decides afresh, counted as `turn_pin`). Every evaluator still runs and is logged; only the route is held, the invariants run again on it, and a **fresh `local-private` always wins** — a pin never moves a turn off privacy (a turn whose first call was private stays private through a nudge). Every later call stores `decisions.pinned_from` = the turn's first decision (a shadow pins from, and points at, its OWN shadow rows) and enqueues NO analysis requests, so one answer costs at most one classification; `route_policy_pinned_total{ruleset, outcome: kept | changed | private}`. No pin without both ids (Claude Code) or for a background task, and never on `/evaluate`. `background_task` on `/decide` is optional (default `false`, so route-policy deploys before LiteLLM) and stored in `decisions.background_task`; an `llm_classifier` neither looks up nor classifies a task and abstains (`background task`), and a task never pins a turn. Recommend Open WebUI Admin Settings → Interface → Task Model = `local-private` (tasks then never reach `auto`, nor Claude). The `/decide` response key set is unchanged. Covered by `test_turns.py` (in-memory tables), `test_pipeline.py`, `test_default_ruleset.py` and `test_db.py`.
- **Phase 5: fast signals, in shadow (`default-signals@1`).** A second shadow slot (`bindings.yaml`: `shadow: [default-llm, default-signals]`; `mode: shadow`, `pin: turn`); `default@3` keeps routing and makes no signals call, so routing is unchanged. Six new evaluator types, each `@declares`-ed: `pii` (`common.pii`'s patterns in-process on EVERY call, plus the `signals` sidecar's NER), `nearest_examples` (chooses its own route: the top-k route when its share of the similarity mass ≥ `min_share`), `prompt_injection`, `language`, and the pure `text_shape` / `context_size`. A new role, **`observe`**: evaluated and logged with its would-be route, ignored by both combiners (no score, force or veto) — how a signal is measured without routing anything; the invariants are unchanged in both copies. The draft, in order: `pii` (force → `local-private`) on email / phone / street address / gov id / card / bank / account numbers in ANY user message (`user_messages: all` — once sensitive data appears the chat stays private) or in a Phoenix / Trino tool result (`tool_results: '(?i)(?:.*[-_])?(?:phoenix|trino)[-_].+'` — Open WebUI's `phoenix_run_query` and an MCP client's prefixed `mcp__claude_ai_Phoenix-MCP__run_query` / `mcp__litellm__trino-run_query` alike, since Claude Code on `/v1/messages` is routed too; web search and fetch results are not scanned), a name only together with a date of birth (`with_person: [date_of_birth]`), a bare name never; `privacy` (`privacy_kw`) still a force; `injection` (`prompt_injection`, `threshold: 0.9`) **observe only — the jailbreak score is logged, never acted on** until a later version changes its role from Trino data; `default@3`'s four code / reasoning / tool / cooldown rows; `topic` (`nearest_examples` over `rulesets/examples/routes.yaml`, ~30 curated PII-free prompts per route via `examples_ref` — inlined as `config.examples` and hashed like `patterns_ref`, so an edited example is a new version; never real prompts or their embeddings, and a test runs `common.pii` over every example); then code shape, language and size, observed. Signals are prefetched like the verdicts: each evaluator's `signal_requests(ctx)` → `pipeline.signal_requests` merges them into ONE request (validation refuses two evaluators asking one task with different parameters) → `service.load_signals` inside `load_context`'s gather, within `ROUTE_POLICY_SIGNALS_BUDGET_S` → `ctx.signals` / `ctx.signals_error` / `ctx.signals_ms`, so the pipeline stays pure; shadows prefetch their own with the same budget, `/evaluate` waits up to 10 s with no deadline, and startup warms the bound rulesets' example sets. No migration: each signal vote's `evaluations.detail` holds its task `status`, `signals_ms`, types, counts, scores and example ids — never text or spans. Promotion is a later, separate `default` version (`ROUTE_POLICY.md § Promoting the signals`). Covered by `test_signal_evaluators.py`, `test_signals.py` (one batched call, dedupe, the budget cut) and `test_default_signals.py` (wiring, the PII rule, observe never routing).
- **The API contract is shared with the LiteLLM client** (ROUTE_POLICY_PLAN § 7, "Phase 2 build spec"): `/decide` takes `{decision_id (a uuid the HOOK makes), requested_model, litellm_call_id, chat_id, message_id, user_id, key_alias, messages, tools, backends, background_task}` and returns exactly `{decision_id, route, mode, apply, ruleset, votes, scores, latency_ms}`; `/observe` returns 202. Both are **idempotent on `decision_id`** (the first write wins; a duplicate `/decide` replays the stored response) and may still arrive in either order — a `/decide` the hook gave up on can land after the fallback answer's `/observe` — so `outcomes` has **no foreign key** to `decisions` on purpose. `unit-tests/route-policy/test_pipeline.py` / `test_api.py` pin the exact key sets; change them only together with the client.
- **Routing rules live in rulesets, never env vars.** `ai/route-policy/rulesets/*.yaml` (+ `patterns/*.yaml` via `patterns_ref`) are baked into the image and seeded at startup; `bindings.yaml` binds `auto` → `default` @ the highest baked version, shadowed by `default-llm`. A pattern file is content of every ruleset that references it (`default`, `default-llm` and `default-signals`): edit one, bump all three versions; an `examples/*.yaml` set (`examples_ref`) is content of `default-signals` the same way. **Versions are immutable**: the content hash is over the resolved document (refs inlined, YAML comments ignored), and a stored id + version whose content differs **stops startup** (`SeedConflict`) — edit anything, bump `version`. **A stored version needs no file**: only the current `default` (3), `default-llm` (3) and `default-signals` (1) are baked in; `default@1` (phase 2), `default@2` (phase 3), `default-llm@1` and `default-llm@2` live on in the database with their decisions and are compiled from there on first use. Keep it that way — an old version's file would freeze the pattern files, whose content every version referencing them hashes. Env vars (`ROUTE_POLICY_DB_*`, `_POOL_MAX`, `_BINDING_REFRESH_S`, `_CLASSIFIER_URL`, `_CLASSIFY_*`, `_ANALYSIS_*`, `_SIGNALS_URL`, `_SIGNALS_BUDGET_S`) are infrastructure only; the classifier's model, criteria and thresholds, and the signal evaluators' model pins, thresholds and example sets, are ruleset config.
- **The `default` ruleset and its pattern files are the only copy of the routing rules** — `priority` combiner, first non-abstaining vote wins: `privacy` (`regex_text` → `patterns/privacy.yaml`, role `force` → `local-private`), `code-text` (`code_kw`, RE2 regexes → `local-code`), `reasoning-text` (→ `local-reasoning`), all on the latest user message; then `code-tools` (a sandbox MCP / Open Terminal tool CALLED in this exchange → `local-code`) and `sticky-code` (a 2-exchange `cooldown` judged by those two → `local-code`; it was 3 until `default@3`); else `local-general` — and one route per turn (`pin: turn`, above). `unit-tests/route-policy/test_default_ruleset.py` checks that every `patterns/*.yaml` regex stays in the RE2 subset (no lookaround, backreferences, atomic / possessive groups, `\Z`; YAML **single** quotes so the backslashes survive — Python `re` accepts more, so this is the portability check), that the real "Scientific Calculator" chat prompts match `code_kw` (or don't), the wiring, fixed routes on ~25 conversation shapes, and the routes of a turn's later calls (a tool round, the nudge, PII mid-turn); `test_evaluators.py` pins the cooldown's verdicts and reasons. Changing a pattern or the wiring means updating those expectations and bumping the ruleset version.
- **Evaluator output shapes are declared beside the producer** — the classifier's `@result_spec` standard: `@declares(OutputSpec(...))` on each evaluator class (`route_policy/evaluators/*.py`), registered by type, served by `GET /evaluator-types`, and checked against the real evaluators by `test_declarations.py`. A new type is a module + one line in `evaluators/base.py::_DECLARING_MODULES` + cases in that test. `regex_text` uses `common.keywordmatch` (Go-RE2 semantics), `tool_calls` / `cooldown` use `common.conversation`, `llm_classifier` reads only `ctx.analyses` (the verdicts the service read for the keys its `analysis_lookups` named) and hands its `analysis_requests` back to be enqueued after the answer — `Evaluator` defaults both hooks to empty, so the pipeline stays pure.

Any Python package or module that could plausibly be reused across multiple projects — current or future — MUST live in `shared/common/`, not in the project directory that first needs it. This includes: scraping / CDP / browser helpers, MCP protocol clients, LiteLLM / model client wrappers, env + logging boilerplate, and cross-cutting utilities.

**Test:** before creating a new module inside `widget/`, `ai/roofix/`, `ai/interceptor/`, or any future project dir, ask *"could a second project want this in six months?"* If yes, it goes in `shared/common/` under an appropriate subpackage and the project imports it via the uv workspace (`common = { workspace = true }` in the project's `pyproject.toml`, backed by the root `pyproject.toml`'s `[tool.uv.workspace]` declaration).

Project-specific business logic (Roofix event parsing, brain decision rules, widget's tray UI, etc.) stays in the project directory — the test is reusability, not size.

Adding a new capability to `shared/common/`: create the subpackage under `shared/common/src/common/<name>/`, expose the public API from its `__init__.py`, add tests under `shared/common/tests/`. No pyproject changes needed in consuming projects unless a new external dep is introduced.

## Classifier result shapes — declared beside the producer

Every structured result the classifier returns has a declared shape, and the standard is: **declare it next to the code that produces it, and register it under the key its consumers look it up by.** An OpenCV detector's `detail` is declared with `@describes(DetectorSpec(...))` on the detector function (`ai/classifier/cv/result.py`); the detector `REGISTRY` is the lookup and `GET /cv-detectors` serves it. A criterion type's `detail` is declared with `@result_spec(ResultSpec(...))` on that type's evaluator (`ai/classifier/analysis/{llm,text,detector,cv}_eval.py`); it registers by type name in `analysis/result_specs.py`, which the aggregator, the scheduler and `GET /criterion-types` look up by. **Every declaration has a test that runs the real producer and compares** — `unit-tests/classifier/test_cv_measurements.py` and `test_result_specs.py` fail on an undeclared key, a missing required key, or a wrong `metric` / `value`. Adding a detector, a criterion type, or a key to an existing `detail` means updating its declaration in the same change; a new type's module is also listed once in `result_specs._DECLARING_MODULES`. `detail.reference` (what a request's saved references did for a unit) is one shared declaration, `REFERENCE_FIELD` in `analysis/result_specs.py`, listed on `LLM_RESULT` only — a `cv` criterion answered by the llm fallback carries it through the llm shape.

## Deploys (`make up`)

`make up <stack> [service...]` runs [`scripts/deploy.py`](scripts/deploy.py) (stdlib Python, docker invoked without a shell), not `docker compose up -d`. Operator guide: [`ai/edge/EDGE.md`](ai/edge/EDGE.md). Three classes, one status line per service:

- **swap** — services labelled `com.zeo.deploy: swap`. A new `<name>-<hash>` copy starts beside the old one (`up -d --no-deps --no-recreate --scale S=<running+1> S`, then `docker rename`), the script waits for its healthcheck (and for the `edge` HAProxy to mark it UP), then `docker stop`s the old copy, honouring `stop_grace_period`. `<name>` is the service key or the `com.zeo.deploy.name` label; `<hash>` covers `docker compose config --hash`, the image ID **and the content of every bind-mounted file/dir inside the repo** — so editing `ai/litellm/litellm_config.yaml` or anything under `ai/litellm/hooks/` and running `make up litellm` produces a new hash and deploys it with no downtime. Already at that hash and healthy → `up to date`. A failed health wait prints the new copy's logs, removes it, leaves the old one serving, and exits 1.
- **oneshot** — `restart` `no` or unset: `up -d --no-deps`, `docker wait`; a non-zero exit stops the deploy.
- **recreate** — everything else, **the default**: `up -d --no-deps S` exactly as before, printing `recreate (downtime): <reason>`. Each recreate-class service has a YAML comment saying why (GPU, Postgres data dir, singleton scheduler, …).

Rules:
- **A swap service never gets `container_name` or `ports:`.** Two copies run at once, so a fixed name collides and a host port can be bound only once. Publish its port through `ai/edge` instead (a `listen <service-key>` section in `ai/edge/haproxy.cfg` + a `ports:` line in `ai/edge/docker-compose.edge.yml`, reusing the existing `PORT_*` variable). It also needs a healthcheck and a `stop_grace_period` covering its longest request. `deploy.py` refuses to swap — falling back to recreate and saying why — a labelled service with `container_name`, `ports:`, a GPU, no healthcheck, `scale > 1`, `network_mode: host|container:|service:`, or `pull_policy: always|build`.
- **New services are recreate by default.** Leave them unlabelled (which also keeps their compose config hash unchanged) unless two copies can safely run at once.
- **Address services by service name, never container name.** Swap containers are `<name>-<hash>`; Docker DNS returns every running copy for the service key. For swap services use `make exec <stack> <svc> CMD='…'` and `make logs <stack> <svc>` (both find the container by compose labels) instead of `docker exec|logs <name>`; recreate-class services keep their fixed names.
- Switches: `RECREATE=1` (plain `docker compose up -d`), `DRY_RUN=1` (print the plan), `FORCE=1` (swap even when up to date). Only the literal `1` turns one on. Tests: `uv run --no-sync pytest unit-tests/deploy -q` (a fake docker runner; no docker needed).
- `edge` is registered last in the Makefile's `STACKS`, so a full `make up` frees the ports before the edge binds them. Its `com.zeo.deploy.wait: healthy` label (honoured on any recreate-class service) makes `make up` wait for its healthcheck and fail loudly if it never passes. Its `com.zeo.deploy.reload: USR2` + `com.zeo.deploy.reload.check: haproxy -c -f …` labels handle a recreate-class service whose config is bind-mounted, which compose can't see change. When compose would leave it running, `make up` runs the check inside it and sends the signal only if the check passes. So editing `ai/edge/haproxy.cfg` and running `make up edge` is a validated, hitless reload. A failed check stops the deploy and leaves the old config serving.
- **A fronted service (one with a `listen <service-key>` section in `ai/edge/haproxy.cfg`) checks the edge before swapping.** If the edge is down, the swap only goes ahead with a warning when the old copy still publishes the port itself (the one-time cutover) or nothing is running yet. Otherwise it refuses unless `FORCE=1`. Once the new copy is up, unreadable edge stats or a running edge without that backend (a stale config) abort the swap like a failed health check. A run that leaves LAN ports without a listener ends with a `WARNING` naming them.
- **`edge-certs` gives the edge real TLS** (`ai/edge/EDGE.md § TLS`). A recreate-class `certbot/dns-cloudflare` loop in the edge stack (`make up edge` deploys it first; the edge `depends_on` it `service_healthy`, which `deploy.py` waits for itself) obtains a Let's Encrypt certificate for `EDGE_TLS_DOMAIN` by DNS-01 through the Cloudflare API, writes `/certs/edge.pem` (the `edge_certs` volume, read-only in the edge) and pushes renewals into the running HAProxy over the admin runtime-API socket in the `edge_api` volume — never `docker.sock`. It is healthy as soon as a certificate file exists (a self-signed placeholder at first), because HAProxy refuses to start on a missing `ssl crt`. A `lan-tls` bind is a LAN bind: the section's allow-list and per-key limit apply to it exactly as to `lan` (only a section that also has an internal bind scopes its rules, with `acl lan_bind so_name -m str lan lan-tls`), and it is published. Adding TLS to another listener is one `bind :<port> name lan-tls ssl crt /certs/edge.pem alpn h2,http/1.1` line plus its `ports:` entry. Editing `ai/edge/certs/*` needs `docker restart edge-certs` (bind-mounted, recreate-class: compose cannot see the edit).
- **The edge also fronts three recreate-class HTTP APIs** — `classifier`, `sandbox-runner`, `detector` — with no `ports:` of their own, so a restart answers `503` + `Retry-After` instead of a refused connection. Those checks are swap-path only, so their deploys never wait on the edge. A `listen` section's FIRST `bind` (`name lan`) is the published LAN port and the only one `deploy.py` reads; a later bind is `name lan-tls` (litellm's `4443`) or, should one ever be needed, `name internal` (never published, its section's LAN rules scoped by `lan_bind`). Internal-only listeners are `frontend` sections (`8404` stats CSV, `8405` Prometheus exporter, `8407` status page) so `deploy.py` never treats them as services. Every LAN bind rejects clients outside `EDGE_ALLOWED_CIDRS`; LiteLLM's LAN bind also caps concurrent requests per key (`EDGE_LITELLM_MAX_CONCURRENT_PER_KEY`). `unit-tests/deploy/test_deploy.py`'s repo-invariant tests enforce all of it.

**Maintenance rule — keep the collections in sync with the code.** Whenever an API endpoint is added, renamed, removed, or changes its request/response shape, path params, query params, auth mode, or headers, update the corresponding `*.postman_collection.json` in the SAME change:

1. Add / update / remove the `item` under the collection's `item` array (or the appropriate subfolder like `MCP`).
2. Match the `request.url.path`, `request.method`, `request.header`, and `request.body.raw` to the code exactly — bodies must be valid JSON matching the current Pydantic / FastAPI model.
3. **Path parameters use `:name`, not `{{name}}`.** Any URL path segment that's a dynamic identifier (session id, job id, message id, filename, etc.) MUST be written in Postman's path-variable syntax — `:sandboxSessionId`, `:jobId`, `:roofixMessageId` — in BOTH `request.url.raw` and each matching entry in `request.url.path`. Add a `request.url.variable` array on the URL object with one `{"key": "name", "value": "", "description": "..."}` entry per path variable so Postman renders the editable field. Keep the corresponding top-level collection `variable` in place too (so users have one default they paste into). The `{{host}}` variable at the start of the URL (`{{litellm}}`, `{{kokoro}}`, `{{roofix}}`, etc.) is the ONLY `{{…}}` form allowed in `url.raw` — it stays as-is. `{{…}}` is also fine in headers, request bodies, query-string values, and auth blocks — the rule is path segments only.
4. Update the item's `description` to say WHAT it does, WHAT it returns, WHAT errors are possible, and reference the endpoint's docs section (e.g. `ENDPOINTS.md § …`).
5. If a new collection-level variable is needed (e.g. a fresh path-param handle like `sessionId`), add it under the collection's top-level `variable` array with a `description` explaining how to populate it.
6. If routing changes (e.g. a service moves onto a new LiteLLM pass-through prefix, or leaves LiteLLM entirely for a direct-service URL), update the collection's base-URL variable AND the `info.description` note about how requests are authenticated.
7. If a NEW service under `ai/` starts exposing an HTTP API, create `{service}.postman_collection.json` alongside its docs, add a row to the **Current collections** table above, and structure it after `sandbox-runner.postman_collection.json`.

Collections are the single source of truth for how each service's API is called from outside — do not merge an API-shape change without updating them. The `*.md` endpoint doc and the `*.postman_collection.json` MUST agree; when they don't, the code is authoritative and both must be corrected.
